# Hosted first-run store demo

Run `.github/workflows/android-device.yml` on a disposable, English Android emulator. Both API 35 and 36 run the Telecom/SystemUI regression and record the first-run demo. `workflow_dispatch` accepts an `app_ref`; pull requests use their candidate commit. For a flavored candidate the workflow builds CommunityDebug for call regression and PlayDebug for the store demo, plus the isolated fixture APK. A pre-flavor revision builds its plain Debug APK and skips the demo. The `baseline_without_phone_permission` negative control also skips the demo; its actual call failure or unexpected pass is reported explicitly. It does not submit a store listing or create a PR.

The recorder requires `--serial emulator-5554 --reset-test-packages`, verifies `ro.kernel.qemu=1`, then force-stops and clears **only** Speedbreaker and the synthetic fixture. It installs both APKs. It does not seed consent, grant Phone permission with `pm grant`, or write Accessibility settings. Do not run it on a personal device. The call regression has its own seeded state and is never used as the demo.

## Recorded sequence

1. Fresh launch shows Welcome. The recorder scrolls through the complete disclosure, including what Accessibility sees, the eight-second lock, and local storage. It captures `welcome.png` and `full-disclosure.png`.
2. It taps **Not now — close**, checks Welcome disappeared, reopens the app, and checks Welcome returned. It scrolls to the disclosure again, captures `acceptance-disclosure.png`, and taps **I understand — continue**. Consent is a real UI action.
3. It opens native Accessibility Settings from the app, turns on Speedbreaker, accepts Android's native warning, and verifies the enabled service. If Android applies the sideload restriction, the documented test-only path is **Open app info → ⋮ → Allow restricted settings** on the fresh emulator, then return to the Accessibility switch. `accessibility-settings.png` shows the switch before consent and `accessibility-enabled.png` after consent. An authentication barrier fails the run; it is never bypassed silently.
4. It taps **Allow call-state access**, grants the native Phone dialog, and verifies Android reports `READ_PHONE_STATE` granted.
5. It searches the app picker for **Speedbreaker test target**, chooses that single synthetic app, and captures `chooser.png` and `home.png`. It opens Defaults and checks **12 seconds** and **Always on** in the actual UI. Those are fresh-install defaults; the recorder does not edit an owner's schedule or app settings.
6. It opens the fixture target, captures `breath-locked.png`, waits for **What are you here for?** after the eight-second lock, and captures `choices-after-eight-seconds.png`. It waits for Continue to become enabled at the end of the 12-second breath. After a native SystemUI shade preflight locates the Settings gear, a second target launch taps that gear during the initial lock and captures `systemui-during-lock.png` and `settings-escape.png`. This escape is a UI gesture, not `adb am start`. Finally it returns through native Settings to turn off Speedbreaker's Accessibility switch, verifies the service is absent, and captures `accessibility-disabled.png`.

`first-run.mp4` is the actual emulator screen recording. `evidence.json` gives UTC timestamps, offsets from recording start, passed assertions, source commit, APK hashes, emulator API/fingerprint, and SHA-256 for each captured file. A failed step leaves `failure.png` and `failure-ui.xml` when possible and fails the job. Read the event offsets alongside the video; recording start and asynchronous Settings transitions make exact screen-frame timing variable. The screenshot images are candidate listing assets from a fresh emulator; inspect them for legibility and any OS-specific dialogs before publication. The video and images have no synthetic overlays or edited consent state.

Use the workflow artifacts named `android-device-api35-<commit>` and `android-device-api36-<commit>` to review the evidence. The regression output is in `build/device-regression/`; the demo output is in `build/store-demo/`. A passing command invocation alone is not evidence: check both GitHub job conclusions, `demo_complete`, all assertion values, video duration/content, and capture hashes. Google APIs imagery, debug build branding, Settings wording, and sideload warnings can differ from a retail Play install. The test target is an inert fixture, not a personal app.
