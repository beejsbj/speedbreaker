# Hosted first-run store demo

Run `.github/workflows/android-device.yml` on a disposable, English Android emulator. Both API 35 and 36 run the Telecom/SystemUI regression and record the first-run demo. `workflow_dispatch` accepts an `app_ref`; pull requests use their candidate commit. For a flavored candidate the workflow builds CommunityDebug for call regression and PlayDebug for the store demo, plus the isolated fixture APK. A pre-flavor revision builds its plain Debug APK and skips the demo. The `baseline_without_phone_permission` negative control also skips the demo. It reports a call failure only when the test GSM call was sent; warmup/setup failures and unexpected passes have separate labels. An old manifest with no Phone permission is treated as absent rather than trying `pm revoke`. It does not submit a store listing or create a PR.

For bounded observer and consent development, a **manual** dispatch can set `demo_only: true`. This skips the seeded call scenarios and writes `build/device-regression/skipped.json` with `SKIPPED_DIAGNOSTIC_ONLY`; it never reports a call pass. It requires a flavored Play APK and cannot be combined with the negative control. Normal push and PR runs always execute all call scenarios on both APIs. The final integrated candidate needs that full gate.
For the SystemUI safety measurement, a manual dispatch may also set `policy_diagnostic_tall: true` with `demo_only: true`. This keeps the emulator's actual 1080×2400 display and runs the real consent, grants, breath, Settings escape, and service-disable sequence. It records `listing_capture_skipped` for each asset and can report only `policy_diagnostic_complete`, never a complete store packet. The normal PR and final runs still require four 1080×1920 JPEGs and `demo_complete`.
The historical negative control refuses stale regression output. Its failure label requires a test call requested by instrumentation, a failing call result, and two successful emulator GSM call acknowledgments for that scenario (warmup then test); a failed injection or old file cannot satisfy it.

The recorder requires `--serial emulator-5554 --reset-test-packages` and verifies `ro.kernel.qemu=1`. After the call regression, it uninstalls and freshly installs **only** Speedbreaker and the synthetic fixture, then force-stops and clears them. This removes runtime grants that `pm clear` alone retains; the recorder verifies Phone is ungranted before asking through the app UI. It does not seed consent, grant Phone permission with `pm grant`, or write Accessibility settings. Do not run it on a personal device. The call regression has its own seeded state and is never used as the demo.

## Recorded sequence

1. Fresh launch shows Welcome. The recorder scrolls through the complete disclosure, including what Accessibility sees, the eight-second lock, and local storage. It captures `welcome.png` and `full-disclosure.png`.
   The observer requires `isVisibleToUser` and positive on-screen bounds for each disclosure section and the acceptance footer. Off-screen semantic descendants do not count as viewed or tappable content.
2. It taps **Not now — close**, checks Welcome disappeared, reopens the app, and checks Welcome returned. It scrolls to the disclosure again, captures `acceptance-disclosure.png`, and taps **I understand — continue**. Consent is a real UI action.
   It waits for the decline transition before checking Welcome closed; a screenshot during that animation does not by itself prove the tap failed.
   The acceptance button must remain enabled at the same visible bounds across two reads. If the first UI tap leaves Welcome open, one more observed tap is allowed; the run requires Home to appear and records each tap.
3. It opens native Accessibility Settings from the app, turns on Speedbreaker, accepts Android's native warning, and verifies the enabled service. If Android applies the sideload restriction, the documented test-only path is **Open app info → ⋮ → Allow restricted settings** on the fresh emulator, then return to the Accessibility switch. `accessibility-settings.png` shows the switch before consent and `accessibility-enabled.png` after consent. An authentication barrier fails the run; it is never bypassed silently.
4. It captures `phone-rationale.png`, taps the live **Allow call-state access** Home button from its actual UI bounds, grants the native Phone dialog, and verifies Android reports `READ_PHONE_STATE` granted. One fixture instrumentation stays alive for the recording and observes hierarchy with `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`. Stock `uiautomator dump` suppresses the service under test; repeatedly starting fixture instrumentation also force-stops the synthetic target. The native dialog and Android grant are required to proceed.
   The observer waits for the Android dialog title and stable Allow button bounds on two reads. If the animated dialog remains after the first UI tap, it permits one more observed tap; no ADB permission grant is used.
5. It searches the app picker for **Speedbreaker test target**, chooses that single synthetic app, and captures `chooser.png` and `home.png`. It opens Defaults and checks **12 seconds** and **Always on** in the actual UI. Those are fresh-install defaults; the recorder does not edit an owner's schedule or app settings.
   On the 1080×1920 listing display, the schedule row is below the fold. The recorder scrolls until it is visibly on screen, captures Defaults, and returns with the Android Back key, checking Home again.
6. It opens the fixture target, confirms the live Accessibility overlay window, captures `breath-locked.png` inside the first eight seconds, `choices-after-eight-seconds.png` after eight seconds of visible overlay, and `choices-ready.png` after the full breath only when the fixture observer reports **Continue** enabled. Review the actual images and video to confirm the labels and timing. It returns Home and calibrates the real SystemUI shade and gear from the launcher; that calibration alone makes no claim about lock escape. A second protected target launch observes the shade after each replayed gesture. If the gear is missing, tall diagnostics save `locked-shade-*.png`, `locked-windows-*.xml`, and `locked-window-*.txt` immediately with elapsed times. If the gear is visible, the recorder taps its current bounds and requires native Settings to resume before eight seconds, capturing `systemui-during-lock.png` and `settings-escape.png`. No saved coordinates or `adb am start` Settings shortcut count as escape. Finally it returns through native Settings to turn off Speedbreaker's Accessibility switch, verifies the service is absent, and captures `accessibility-disabled.png`.

`first-run.mp4` is the actual emulator screen recording. `evidence.json` gives UTC timestamps, offsets from recording start, passed assertions, source commit, APK hashes, emulator API/fingerprint, and SHA-256 for each captured file. A failed step leaves `failure.png`, `failure-ui.xml`, an all-window hierarchy, and SystemUI/window/Accessibility diagnostics when possible and fails the job. The all-window dump records window type, package, active/focus state, layer, and bounds; it is read-only and does not drive a fake escape. Read the event offsets alongside the video; recording start and asynchronous Settings transitions make exact screen-frame timing variable. The video and images have no synthetic overlays or edited consent state.
The recorder refuses a nonempty output directory, records to a unique remote MP4 path, requires a successful nonempty pull, and validates MP4 structure before a video can pass. It requires Android Settings to be the resumed activity before eight seconds from the protected launch; a late transition cannot count as a hard-lock escape. Existing evidence is never deleted to make a rerun pass. Failure diagnostics run `dumpsys` through `adb shell` and record collection failures with status and stderr rather than leaving silent empty files.

The `listing/` folder holds four actual emulator JPEG screenshots: Welcome, Home with only the synthetic target, Defaults, and ready choices. The disposable AVD display is set to 1080×1920 with `wm size` before the demo. API 36 uses Android's shell `screencap -j`; API 35 uses the persistent fixture's `UiAutomation.takeScreenshot()` and Android `Bitmap.compress(JPEG, 95)`, since its shell command does not support JPEG. Neither path crops or edits the rendered UI. The recorder checks JPEG encoding and 1080×1920 dimensions, records the capture method and each SHA-256, and resets the AVD display afterward. These are unedited candidate assets; review the actual images and Google Play listing requirements before publication. Policy evidence PNGs remain separate. A failed listing capture does not interrupt policy diagnosis, but the completed demo fails unless all four JPEGs are present.

Use the workflow artifacts named `android-device-api35-<commit>` and `android-device-api36-<commit>` to review the evidence. The regression output is in `build/device-regression/`; the demo output is in `build/store-demo/`. A passing command invocation alone is not evidence: check both GitHub job conclusions, `demo_complete`, all assertion values, video duration/content, and capture hashes. Google APIs imagery, debug build branding, Settings wording, and sideload warnings can differ from a retail Play install. The test target is an inert fixture, not a personal app.
