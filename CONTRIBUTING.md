# Contributing to Speedbreaker

Bug reports, device observations, and clear suggestions help make Speedbreaker
more dependable. You do not need to build the app to contribute a useful report.

## Report a problem

Check the [setup guide](docs/getting-started.md) and
[existing issues](https://github.com/beejsbj/speedbreaker/issues) first. If the
problem is new, use the
[bug report form](https://github.com/beejsbj/speedbreaker/issues/new/choose).
Include the app version, phone model, Android version, steps to reproduce,
expected result, and actual result. Say whether you use gesture navigation,
navigation buttons, split-screen, or picture-in-picture when relevant.

Screenshots are optional. Remove names, notifications, account details, and
other personal information before posting; GitHub issues are public. Do not
upload a full device bug report or unreviewed logs. Use
[the security policy](SECURITY.md) for vulnerabilities or exposed credentials.

The eight-second opening lock and One Hand Operation+ being unavailable while
the overlay is visible are documented behavior. Targets and redirects are
chosen by the user. If the app differs from the documented behavior, describe
that difference.

## Suggest a change

Explain the situation you want to improve and what you would expect to happen.
For substantial features or behavior changes, open a feature request before
investing in an implementation. The [interaction contract](docs/interaction-contract.md)
sets the current behavior; its October release clarification supersedes older
trial requirements. The [UI notes](docs/design/calm-ui.md) explain the visual
choices.

## Work on the code or docs

Speedbreaker is licensed under [Apache License 2.0](LICENSE). Contributions
should be compatible with that license. Preserve third-party copyright, license,
and attribution notices; identify any new dependency or copied material and
its license in your pull request.

For development, start with [Build and test](docs/build-and-test.md). The app
uses Kotlin and Jetpack Compose. The [implementation boundaries](docs/implementation-boundaries.md)
map observation, enforcement, persistence, system actions, and presentation.
`reference/ai-studio/` is historical design material, not the production app.

Keep pull requests focused on one problem. Explain the behavior before and
after, why it changes, and what you checked. Include a regression test when a
behavior change needs one; documentation edits need link and wording checks,
not a full Android build. For visible UI changes, include relevant screenshots
and check large text and landscape layouts.

For app changes, run the relevant tests and lint as described in the build
guide. Clearly distinguish automated checks from behavior observed on a phone.
A passing test suite does not establish that calls, gestures, reboot recovery,
or background operation work on a particular device. Report any checks you
could not run.

Keep credentials, signing keys, local SDK paths, APKs, and private device logs
out of commits. Review `git diff` and `git status` before submitting, including
any screenshots regenerated by tests.
